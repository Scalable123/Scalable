# T001 — Pinterest account linking and user-directed board import

Date: November 14, 2026. Status: implemented and verified with mocked providers; live access disabled pending approved configuration.

The original Supabase bearer-token identity boundary recorded below was superseded by the follow-up GraphQL-hosted ASP.NET Identity cookie integration. Current setup instructions are in `docs/PINTEREST-INTEGRATION.md`.

## Scope and decisions

- Read `docs/FRONTEND.md`, `documentation/FRONTEND.md`, `docs/PINTEREST-INTEGRATION.md`, and the account/deployment handoffs before implementation. No AGENTS.md was found. Preserve the existing README edits and untracked comprehensive frontend documentation.
- Add the documented C# / ASP.NET Core backend rather than putting Pinterest secrets or token exchange into browser JavaScript. Retain Supabase as the application identity provider; validate application bearer tokens server-side.
- Support only explicit account linking, listing the authenticated user's boards, reviewing their pins, and copying selected references into Scalable. Never modify or delete original Pinterest boards.
- Exclude Pinterest from AI discovery, search, crawling, image analysis, and training. Imported provider content is display-only; it is never sent to the research service. Do not expose generic provider proxy/search endpoints.
- Keep the local demonstration as an explicitly separate fallback. Never infer a real connection from demo state or fall back to sample content after a live request fails.
- Use read-only OAuth scopes, browser-bound expiring single-use state, server-side encrypted SQL credential storage, token refresh, bounded provider requests, and per-user authorization. Keep provider credentials out of responses, browser storage, logs, and static publication artifacts.
- The current canvas and board persistence are local. Import all pages before committing selected references to the canvas; cancellation/errors must not commit a partial board. Unsupported pins must be counted truthfully. Durable cloud board storage/import jobs remain a separate feature.
- Pinterest's developer website is blocked by the environment's outbound network policy. Use the official Pinterest OpenAPI repository as the next available technical reference. Current developer approval, contractual permission, media retention rules, and actual account eligibility cannot be established by code or mock tests. Keep live access disabled until the operator explicitly confirms permitted use and configures credentials.
- Use .NET 10 and Microsoft.Data.Sqlite 10.0.15. The first package choice (10.0.0) failed the dependency vulnerability audit through its bundled SQLite; use the patched release and keep warning-as-error builds. The workspace had no .NET SDK; install it under ignored `work/`, with writable XDG/.NET/NuGet paths, rather than writing to the user's home.
- Request only `boards:read,pins:read,user_accounts:read`. Verify board owner against the linked Pinterest username; exclude other owners' group boards and content unavailable under the approved scopes. No write or secret-board permissions and no arbitrary URL/resource proxy.
- Follow the official specification's continuous-refresh contract. Preserve rotated refresh credentials, serialize refresh/disconnect in this single-instance backend, and report revoked/expired access truthfully. Pinterest's revoke endpoint supports system-user tokens only: disconnect locally and explain how to revoke in Pinterest settings instead of inventing a user-token revocation request.
- Protect cursor values for their application user and board/resource. Bound page count, total identities, response size, timeouts, and per-owner requests; forward provider Retry-After and let users retry rather than run automatic provider request loops.
- Copy only supported image references, keep original Pin and creator links, all source-board associations, and explicit unknown reuse rights. Exclude video/carousel/missing or untrusted-host media with visible counts. Do not download/cache images or fabricate board URLs.
- Set `researchAllowed: false` on every Pinterest import. Never include imported items in research requests. Leave the brief blank on new live-import boards so provider titles/descriptions cannot become AI input. Add guards at both existing research adapters and require equivalent enforcement in future server workers.
- Maintain the existing local board persistence rather than introducing an unrelated cloud-board system. Fetch all pages before review and local commit. Durable import jobs are deliberately deferred with cloud board saving; this task supplies complete synchronous traversal with progress and abort semantics.
- Package the frontend with the API for a same-origin deployment, preserving static-only samples. Disable unused static-asset manifest processing after publish validation exposed a missing source wwwroot assumption; use the explicit physical-file provider. Exclude runtime data/keys from version control and publish content.
- Keep credentials encrypted in SQLite with per-owner ASP.NET Data Protection purposes. The private key volume also needs host filesystem controls/encryption; local development keys are not independently KMS-wrapped. This implementation is for one API instance; distributed refresh/credential coordination is future scaling work.
- Update Pinterest, frontend, account, deployment, README, and comprehensive documentation, preserving the user's existing README addition and documentation baseline. Correct stale provider claims in the Studio About and account connection text.
